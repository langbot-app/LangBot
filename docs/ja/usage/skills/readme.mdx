---
title: "スキル (Skills)"
description: "LangBot の Skills を活用し、専門知識を必要に応じて読み込み。コンテキストを圧迫せず AI Agent を拡張。"
---

Skill は**必要時に起動する**指示パックです。ユーザーのリクエストが該当する内容になると、Agent が `activate` ツールを呼び出してその Skill の指示をコンテキストに取り込み、それに従ってタスクを完了させます。起動されていない Skill はコンテキストを消費しません。

Agent に**専門的なワークフロー、テンプレート、スクリプト**を一つ追加するのに向いています。たとえば「Python プロジェクトの解析」「PDF フォーム入力」「コードレビュー」など。System Prompt に全部詰め込む必要はありません。

## プラグイン・MCP との違い

| やりたいこと | 使うもの |
|------|------|
| 必要時に起動する一連のワークフロー（スクリプトやテンプレート付き可） | Skill |
| 既存の MCP ツールサービスに接続 | MCP サーバー |
| 長期常駐機能、設定画面、イベント、ナレッジベース | プラグイン |

詳細は[ランタイムと拡張機能の関係](../sandbox/runtime-relationships)を参照。

## lbctl でローカルパッケージを更新

編集前に現在の Skill リビジョンを取得し、完全なディレクトリと一緒に指定します。

```bash
lbctl skill get demo -o json
lbctl skill push demo --dir ./demo --base-revision <revision> --dry-run
lbctl skill push demo --dir ./demo --base-revision <revision>
```

プレビューは `SKILL.md` を検証し、追加・変更・削除するファイルと公開権限を表示します。パッケージ内の名前は `demo` と一致する必要があります。公開はバイナリ資源と実行権限を含むパッケージ全体を原子的に置き換え、ローカルに存在しないファイルを新バージョンから削除します。`resource.manage` と `resource.view` が必要で、CLI は公開後のリビジョンを読み取って検証します。リビジョン競合時は最新パッケージを取得して変更を統合し、確認したリビジョンで再試行してください。実行中の処理は固定された既存バージョンを使用します。

## Skill のインストール

<Note>
Skill の管理、有効化、読み取り専用リソースへのアクセスは Core が提供し、Box は不要です。スクリプト実行、サンドボックス内の下書き編集、`register_skill` には利用可能な Box が必要です。詳細は[サンドボックス設定](../sandbox/config)を参照。
</Note>

### LangBot Space から（推奨）

[LangBot Space](https://space.langbot.app) は LangBot 公式のマーケットプレイスで、すぐに使える Skill が多数掲載されています。WebUI の Skills ページから閲覧して 1 クリックでインストールでき、`SKILL.md` の作成やリソースファイルの準備は不要です。

ほとんどのケースはこれで十分です。独自のワークフローが必要な場合は下記の方法を使ってください。

### 自分で作る

**WebUI** — Skills ページで新規作成、zip アップロード、GitHub からのインポートが可能。

**サンドボックス + `register_skill`**：
1. サンドボックスの `/workspace` 配下にディレクトリと `SKILL.md` を準備
2. Agent に `register_skill(path="/workspace/my-skill")` を呼び出させる

いずれの方法でも Core が管理する Skill リポジトリに公開されます。

### データベース保存とアップグレード

新規インストールはデータベース保存とネットワーク転送が既定で、オブジェクトストレージは任意です。既存設定の選択は維持され、新項目のない旧設定はローカル保存と `legacy` を使います。下記の設定に切り替えると、Core はサービスを開始する前に読み取り可能な旧 Skill とローカル資産を移行します。登録情報、不変のバージョンパッケージ、永続添付データはこの保存層を使います。ソースからのインストールは `uv sync` で同じチェックアウトの SDK を自動的に使用します。別途配置した Runtime には対応するソースまたは公開済み SDK が必要です。[ランタイム開発手順](../../develop/plugin-runtime)を参照してください。複数の Core は同じ外部 PostgreSQL、論理インスタンス ID、認証設定を使用します。`data/config.yaml` を変更して Core を再起動します。

```yaml
skills:
    persistence: database
    root: './data/skills'  # 新規構成の例。更新時は元のルートを維持
storage:
    use: persistent
    content:
        backend: database
```

対応する Core と Box Runtime では `box.file_transfer_mode: network` を明示的に設定できます。Core は実行に固定したパッケージを転送し、Box が検証・キャッシュして読み取り専用でマウントするため、Skill や作業ディレクトリの共有は不要です。データベースとネットワーク方式の組み合わせでは有効化と実行で `skills.root/.database-cache` を作りません。Agent のリソース一覧はデータベース内の正規の不変マニフェストだけを検証し、パッケージ本体を取得しません。内容の読み取りは検証済みのメモリ内パッケージを再利用できますが、毎回データベースのアクセス権とバージョン記録を確認し、全バイトを検証します。ローカル永続キャッシュは作りません。一覧、有効化、キャッシュからの読み取りは保存元の正常性チェックではなく、保存元が利用不能・破損していても成功する場合があります。コールド読み取り、再起動、キャッシュの追い出し後は保存元から再取得・検証します。Runtime の実行時検証も引き続き全バイトを対象とします。`register_skill` は完全な下書きをネットワークで取得し、旧パッケージを読まずに検証後に一度で公開します。過去のバージョンは保持され、公開しても実行中のバージョンは変わりません。実行終了時にはその実行の入力・出力・スナップショットを削除し、下書きは Box セッション終了まで保持します。セッションの期限切れや削除で作業ディレクトリも消えるため、残すファイルは先にエクスポートしてください。明示された既存の `legacy` 設定は共有マウントとキャッシュ動作を維持します。別途配置した Runtime にも対応する SDK が必要です。旧 Runtime はネットワーク作業領域の設定に対応しません。

オブジェクトストレージを使う場合は、`storage.content.backends.<名前>` に `type: s3`、`endpoint_url`、`bucket`、`region`、`access_key_id`、`secret_access_key` を設定し、`storage.content.backend` をその名前に変更します。過去の名前と endpoint/bucket/region は維持してください。書き込み先の切り替えは既存データを移動せず、古い設定の削除や接続先変更で該当コンテンツを保存元から再取得できなくなります。認証情報の変更後は Core を再起動します。

データベース保存のバージョンパッケージは最大 64 MiB です。ネットワーク方式の `register_skill` 下書きは非圧縮 ZIP で、20 MiB、512 エントリ、1 ファイル 16 MiB、ディレクトリ深度 16 が上限です。Box のファイル転送設定がより小さい場合はその上限も適用され、拒否された下書きは保持されます。同時更新による競合上書きは拒否され、実行中のタスクは固定済みのバージョンを使用します。

Runtime は作業領域にスナップショットを作らず、メモリ内で下書きをアーカイブします。Docker 内の別 UID が所有する非公開ディレクトリの回収には、Docker 25+、イメージ内の Python 3、`VOLUME` 宣言のないイメージが必要です。UID/GID マッピングや隔離ポリシーで安全に削除できない場合、Box は再利用不可のままエラーを報告し、再試行または管理者の保守を待ちます。


### 既存環境の移行

旧ローカル資産の移行には現在 Linux/POSIX の安全なファイルアクセスが必要です。既存 Windows 環境は元の方式を維持するか、Linux で移行してからデータベースに接続できます。ネットワーク実行には POSIX Box Runtime が必要で、Windows Core はリモート Runtime に接続できます。

旧 Core の書き込みプロセスをすべて停止してから更新し、最初に移行用インスタンスを一つ起動します。`skills.root` は**元の Skill ルート**を指定してください。そのインスタンスで `skills.migration.require_source: true` と `storage.migration.require_source: true` を設定し、旧 Skill ボリュームと `data/storage` を保持します。各チェックは対応する旧データがある場合だけ有効にします。新しいレプリカは既定で旧ボリュームを必要としないため、空ディレクトリだけで履歴の完全性は確認できません。

現在の登録、削除済み登録を含む保持バージョン、revision digest、メディア URL、非公開添付キーを維持します。内容の各バッチと進捗を同じトランザクションで保存し、中断後の再起動で再開します。移行元の変更、名前の競合、破損パッケージ、必須ボリュームの欠落は起動を停止します。データベースのリースは新しい移行処理の並行実行を防ぎますが、旧プロセスを停止できないため保守中は必ず停止してください。検証完了後にサービスを開始し、完了記録以降のレプリカは旧ボリュームに依存しません。非対応 Runtime ではネットワーク方式の起動を停止します。実行が不要なら `box.enabled: false` を指定できます。

ネットワーク方式では Core に Box ボリュームは不要です。既存の Compose/Kubernetes 定義は旧方式との互換性のため共有を残しています。移行の検証後、Core の専用 Box マウントと対応する同一ノード親和性を外せます。新規構成は Core データと Box を別ボリュームにしてください。Docker daemon を使う Box には daemon と同じ絶対パスのボリュームが引き続き必要です。定義は `LANGBOT_BOX_CONFIG` で Runtime 独自のルートを設定します。アップグレード時に既存 Box のボリュームやインスタンス ID を置き換えないでください。

資産の自動移行はインスタンスの所有権を検証できるローカルファイルだけが対象です。Workspace 情報のない旧メディアは OSS の単一 Workspace のみで取り込み、複数 Workspace の所有者を推測しません。既存の明示的な S3 設定は維持され、`storage.use` の変更だけでは旧 S3 オブジェクトを移動しません。

旧ディレクトリと保守開始時のデータベース復元点を保持してください。新方式の書き込みは旧ディレクトリに反映されません。旧版へ戻すには復元点と旧設定を一緒に戻すか、新バージョンと資産を先にすべてエクスポートして復元します。`filesystem` / `local` に戻すだけでは新しい書き込みが見えなくなります。本変更は Box 関連ファイルの分離であり、設定、プラグインの非公開データ、他の Core サブシステムは各自の永続化要件に従います。


## パイプラインで有効化

Skill をインストールしたあと、パイプラインの拡張設定で Agent から見える Skill を決めます：

- 「すべての Skill を有効化」をオンにする、または
- 指定した Skill のみをバインドする

バインドは `<available_skills>` 一覧（Agent が選択肢として認識する対象）にのみ影響します。完全な指示は常に `activate` が呼ばれた後に注入されます。

## SKILL.md を書く

Skill はディレクトリと `SKILL.md` 1 つで構成されます。frontmatter にメタデータを書き、本文は Agent が起動後に受け取る指示です：

```markdown
---
name: code-reviewer
display_name: コードレビューアシスタント
description: コードをレビューして改善提案を行う。ユーザーが review、レビュー、コード改善に言及したときに起動
---

## 実行手順

1. `read` で関連ファイルをざっと確認
2. 可読性、潜在的なバグ、セキュリティ問題をチェック
3. 優先度順に改善提案を提示
```

LangBot は現在、以下の 3 つのフィールドを読み取ります：

| フィールド | 必須 | 説明 |
|------|------|------|
| `name` | 作成／登録時 | 一意の識別子、1–64 文字 |
| `description` | 強く推奨 | Agent はこれをもとに起動可否を判断する——具体的なほど選ばれやすい |
| `display_name` | 任意 | UI 表示名 |

`description` は Agent が Skill を選ぶ唯一の手がかりです。**機能・適用シーン・想定されるトリガーワード**を具体的に書きましょう。

完全な仕様は [agentskills.io](https://agentskills.io/home) を参照してください。その他のフィールド（`license`、`metadata` など）は将来の互換のために残せますが、現在は読み取られません。

**リソースを伴う Skill** では `SKILL.md` と同じ階層に `scripts/`、`templates/` などを置きます。実行には有効化結果が返す固定バージョンのパスを使用します。

### Agent が使えるツール

| ツール | 用途 |
|------|------|
| `activate` | Agent が該当を判断したときに自動で呼び出し、SKILL.md をコンテキストに取り込む |
| `register_skill` | サンドボックスに用意したディレクトリを新しい Skill として登録 |

## LangBot Space に共有

スキル詳細ページの「Space に共有」から、現在の Skill パッケージをマーケットに投稿できます。ダイアログに送信するファイルが表示され、API キーやトークンなどの認証情報を含む場合は投稿できません。スクリプトと外部通信の審査を通過すると、LangBot Space のクリエイター名義で公開されます。同じ名前で再度共有すると新しいバージョンになります。

## よくある問題

| 症状 | 確認項目 |
|------|--------|
| Skill 一覧が空 | Workspace、Skill のバインド、`skills.persistence` と `skills.root` |
| Agent が Skill を起動しない | `description` が具体的か、パイプラインでバインドされているか、モデルが関数呼び出しに対応しているか |
| 起動後にファイルが見つからない | ファイルは Skill パッケージ内に置き、有効化結果が返すバージョンのパスを使用する |
| `register_skill` がエラー | パスは `/workspace` 配下である必要があり、ディレクトリまたは 2 階層以内のサブディレクトリに `SKILL.md` が必要 |

<Note>
自動有効化には Skill とツール呼び出しに対応する Runner が必要で、スクリプト実行には Box が必要です。外部 Runner（Dify、n8n、Langflow、Coze など）では各プラットフォームが対応する仕組みを利用してください。
</Note>
