---
title: "System Compatibility"
---

LangBot's plugin system uses `Asyncio` and `Subprocess`. Windows' default `ProactorEventLoop` does not support the stdio transport on the *passing pipes* side, and `SelectorEventLoop` — which does not support `Subprocess` either — is no alternative. Historically that made the normal stdio transport unusable on Windows.

For background, see the [Python documentation](https://docs.python.org/3.13/library/asyncio-platforms.html).

## How Windows is handled today

Windows is no longer special-cased at the transport level. The rule is the same on every OS:

- **a runtime that LangBot launches itself always uses stdio**;
- **only a runtime LangBot does not launch uses WebSocket** — Docker Compose, a `--standalone-*` process, or an explicit `runtime.endpoint`.

The Windows stdio problem is solved inside the runtime itself: the stdio server runs its pipes on worker threads instead of registering them with the Proactor IOCP (`langbot-plugin-sdk` `f5a079811`, shipped from SDK `0.6.0-beta.1` and adopted by LangBot 4.11.0-beta.1). Pinning an older SDK reintroduces the original `WinError 6` / `_ProactorReadPipeTransport` failures.

Nothing needs to be configured; the transport follows who launches the runtime, not which OS you are on.
