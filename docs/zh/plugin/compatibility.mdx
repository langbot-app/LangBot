LangBot 插件系统运用了 `Asyncio` 和 `Subprocess`。Windows 默认的 `ProactorEventLoop` 在管道一侧不支持 stdio 传输，而 `SelectorEventLoop` 又不支持 `Subprocess`，因此历史上 Windows 无法使用正常的 stdio 传输。

背景请参阅：[Python 官方文档](https://docs.python.org/zh-cn/3.13/library/asyncio-platforms.html)

## 现在如何处理 Windows

Windows 在传输层不再被特殊对待，各平台统一为一条规则：

- **LangBot 自己拉起的 runtime 一律使用 stdio**；
- **只有 LangBot 不拉起的 runtime 才使用 WebSocket** —— Docker Compose、`--standalone-*` 进程，或显式配置的 `runtime.endpoint`。

Windows 的 stdio 问题改为在 runtime 内部解决：stdio 服务端把管道放到工作线程，而不再注册到 Proactor IOCP（`langbot-plugin-sdk` `f5a079811`，自 SDK `0.6.0-beta.1` 起，LangBot 4.11.0-beta.1 已采用）。若把 SDK 钉在更老的版本，原来的 `WinError 6` / `_ProactorReadPipeTransport` 失败会重新出现。

无需任何配置：传输方式取决于谁拉起 runtime，与操作系统无关。
